## Anti-Patterns Verdict

**Does it look AI-generated?** Less generic than before, but more at risk of looking over-designed. The deep green control-room background gives archLoop a stronger identity. The cost is visible: cream panels, diagonal/grid background lines, 1px borders plus 44px shadow blur, tiny labels, and repeated uppercase eyebrows push it toward a stylized AI-tool aesthetic instead of a quiet operator console.

**LLM assessment:** The biggest design issue is still priority. Hub wants to be a high-trust execution console, but too many safety explanations, disabled commands, fallback strings, and decorative environment cues are visible at the same level as live work state. The interface proves its safety model, then keeps proving it.

**Deterministic CLI scan:** 2 findings, both `side-tab` in `hub-desktop/src/styles/hub-desktop.css` at lines 845 and 849 (`border-left: 3px` on sync panels).

**Browser overlay evidence:** Headless injection succeeded on Overview, Task Board, Run Workbench, and Proposal Session after mutable DOM preflight. Console counts were Overview 19, Task Board 12, Run Workbench 23, Proposal Session 9. Main runtime rules: `low-contrast` (`#fffaf0` on `#b56a3c` around 4.0:1, `#fffaf0` on `#2f6bff` around 4.3:1, `#71695e` on tinted panels around 4.2-4.4:1), `tiny-text`, `gpt-thin-border-wide-shadow`, `line-length`, `side-tab`, `cramped-padding`, and `overused-font`. `overused-font` is a weak signal for product UI; the contrast and shadow findings are real.

## Overall Impression

The new direction has a pulse: archLoop now reads more like a command center for autonomous engineering than a stock admin dashboard. That is a win. But the UI has crossed from "restrained dense tool" toward "themed control room" before the layout and accessibility fundamentals are settled. Fix structure first, then decide how much of the new atmosphere the product can afford.

## What's Working

- The control-room palette makes archLoop more recognizable and better aligned with "reliable automated engineer" than the previous generic slate UI.
- The shell model is still credible: rail, header, main area, and inspector match the desktop control-plane contract.
- Run Workbench remains the strongest workflow surface: context, gate, actions, and terminal output have a clear story.
- Preview-confirm appears as a real product safety principle, not an afterthought.

## Priority Issues

### [P1] Compact shell preserves desktop chrome and blocks the workspace

**Why it matters:** On mobile, the app can start with the inspector drawer covering the active view, and the rail can still appear as a right-side implicit column. The refreshed mobile screenshot shows the workspace squeezed while navigation chrome sits on the right.

**Fix:** Default inspector closed below the tablet breakpoint. Replace the desktop rail with a bottom bar, top segmented nav, or menu button on compact layouts. Keep the main workspace full-width before any drawer opens.

**Suggested command:** `$impeccable adapt hub-desktop`

### [P1] Task Board is still not Kanban-first

**Why it matters:** The board is the primary task scanning surface, but create/triage controls and filter copy consume the first row and overflow badly on tablet/mobile. At 390px the toolbar copy still measures around 932px wide.

**Fix:** Move Create Task into a compact row or drawer, collapse advanced filters on narrow screens, keep Run Triage out of the main board toolbar unless actionable, and start the Kanban columns immediately after a slim control strip.

**Suggested command:** `$impeccable layout hub-desktop/src/components/views/TaskBoardView.tsx`

### [P1] Proposal Session decision bar can obscure the primary decision

**Why it matters:** Approval is the highest-stakes action on the Proposal Session screen, but the sticky decision bar can overlay lower content and visually clip the primary apply path when the inspector is open.

**Fix:** Put the decision bar in normal grid flow or reserve bottom space equal to its height. In inspector-open desktop widths, use a two-column action layout that guarantees Approve/Preview/Confirm stays fully visible.

**Suggested command:** `$impeccable polish hub-desktop/src/components/views/ProposalSessionView.tsx`

### [P2] The new visual identity is stronger but too atmospheric for a product surface

**Why it matters:** The deep grid/diagonal background and high-shadow cream panels create memory, but they also compete with task state. On mobile, the background lines become one of the loudest visual elements.

**Fix:** Keep the dark control-room shell, but reduce the background pattern to a quieter texture or remove it behind active work areas. Replace wide decorative shadows with tonal layers or tighter shadows. Let state color, not atmosphere, carry attention.

**Suggested command:** `$impeccable quieter hub-desktop/src/styles/hub-desktop.css`

### [P2] Accessibility and token migration are not finished

**Why it matters:** The refreshed detector found multiple contrast misses and a new `1px border + wide shadow` pattern. The source also shows new tokens in `:root` / `HUB_DESKTOP_TOKENS` while many component rules still hard-code the old slate/blue values.

**Fix:** Add role-specific text tokens for accent, copper, warning, danger, muted-on-tint, and dark-shell contexts. Replace hard-coded old colors with semantic tokens in one pass, then verify contrast on all tinted states. Set 12px as the practical UI-label floor.

**Suggested command:** `$impeccable audit hub-desktop`

### [P2] Header actions create weak affordance and repeated choices

**Why it matters:** Header controls include Sync, Run Flow, inspector, notification/help/account buttons, plus local tabs and rail navigation. Many are disabled or repeated, so the primary next action is less obvious than it should be.

**Fix:** Keep one dominant sync preview affordance, move future/disabled utilities behind a menu, and make the Project/Run/Batch switcher subordinate to the rail or replace one nav system with the other.

**Suggested command:** `$impeccable distill hub-desktop/src/components/HubHeader.tsx`

## Persona Red Flags

**Alex, power maintainer:** Wants to scan task state and recover failures quickly. Red flags: Task Board hides board priority behind create/triage controls; header has too many low-value buttons; no visible keyboard-oriented command path beyond CLI copy.

**Jordan, first-time maintainer:** Needs confidence before approving local writes. Red flags: CLI fallback copy appears everywhere, making it hard to tell which actions are truly desktop-supported; Proposal approval can be partly obscured exactly when confidence matters.

**Sam, cautious release owner:** Needs evidence, reversibility, and safe mutation boundaries. Red flags: preview-confirm is present, but repeated Sync/Run disabled controls make it harder to know which mutation path is authoritative.

## Minor Observations

- The `aL` mark is more visible in the new shell, but still feels like a placeholder brand mark.
- Custom nav/header icons are serviceable but less polished than a standardized icon family.
- The repeated `.hub-eyebrow` pattern is acceptable in small doses but overused as section scaffolding.
- Favicon 404 appears in browser evidence; low severity, easy cleanup.
- The old static `gui/` prototype should remain out of scope for current UI quality decisions.

## Questions to Consider

- What if the dark control-room identity stayed, but active work surfaces became calmer and more information-led?
- Should Task Board optimize for creating tasks, or for scanning and choosing already-existing work?
- Is the inspector a persistent desktop affordance only, or should compact layouts treat it as a deliberate secondary mode?
