---
title: Run flows
description: Reference for project-centric Hub flow execution and output modes.
---

```bash
npx archloop run [<project> | --project <name>] --flow <id>
```

Common flow IDs are `no-review`, `with-review`, `triage`, and
`prd-decomposition`. Proposal flows also accept `--input <value>`.

| Option             | Purpose                                                                     |
| ------------------ | --------------------------------------------------------------------------- |
| `--dry-run`        | Print the run plan without starting agents                                  |
| `--yes`            | Skip the interactive start delay and approve allowed non-interactive writes |
| `--batch-strategy` | Choose planned, limited, or conservative task selection                     |
| `--max-tasks`      | Limit tasks in one batch                                                    |
| `--max-batches`    | Limit batches in one run                                                    |
| `--idle-timeout`   | Override the agent idle timeout in seconds                                  |
| `--output`         | Select `auto`, `plain`, or schema-versioned JSONL output                    |
| `--no-color`       | Disable color styling for flow output                                       |

Task-board flows recover an unfinished same-flow merge-ready batch before
claiming new work. Planned selection recovers an `explicit_blocker` deferral
when live board description and blocker metadata show no effective blocker,
and keeps the deferral when the candidate is a real dependency of a selected
task. Proposal flows reject task-batch options that do not apply.

At startup, task-board runs also detect tasks left in implementation, review,
or merge without a live worktree lease. The event-aware recovery route resumes
after a completed phase instead of repeating it and reuses preserved branch or
worktree changes. Plain output summarizes each route; schema-versioned JSONL
includes the result in the final `autoRecover` projection.

The final `fix` guidance distinguishes semantic failure from interruption. A
real failed task points to `archloop tasks recover --stale`; a run interrupted
without failed tasks points back to `archloop run`, which performs automatic
startup recovery.

Eligible merge-ready tasks each own a durable landing transaction onto a
Hub-managed local Git ref. Merge-ready tasks for one publish target receive
durable FIFO and dependency tickets; later transactions cannot overtake an
older eligible queue head. Hub builds a bounded speculative candidate chain
where each candidate is based on its predecessor OID, schedules full
verification of exact candidate OIDs concurrently where dependencies permit,
and still serializes landing at the queue head with fenced compare-and-swap
evidence. Speculative verification alone never advances the publish target.
Predecessor repair, failure, committed host contribution, or target drift
invalidates only the affected speculative suffix; independent successors
rebuild and reverify while dependents stay blocked until their prerequisite
ships. Committed behind, descendant, and diverged host-target tips are
reconciled into the canonical chain and fully verified before task candidates
continue; uncommitted host state is neither imported nor modified. After a
host contribution lands, reconciliation finishes that synthetic transaction
internally without Beads close or `tasks recover`. A deterministic host-target
merge conflict stays `host_contribution_conflict` (pending, not failed or
shipped): resolve the conflict on the host or publish target, then rerun the
same flow — do not run `tasks recover`. A
queue-head activation performs at most three immediate target-drift rebuilds
with jittered backoff, then retains its ticket in `target_quiet_wait` without
a busy loop or later-task overtaking. A subsequent stable target window starts
a new activation automatically without resetting semantic repair budgets or
requiring `tasks recover`. Plain and JSON output show FIFO position,
predecessor and candidate OIDs, suffix invalidation, host contribution,
verification concurrency, and quiet-wait state. archLoop freezes source and
base OIDs, builds and verifies the exact candidate in a Hub-owned detached
worktree, then advances the publish target, fence, and landing receipt in one
Git ref transaction before closing the task. The user's checkout, index, HEAD,
and WIP are not modified during that landing transaction. After landing, Hub
enqueues a durable checkout projection. A local host branch that is not
checked out anywhere advances with OID compare-and-swap. A checked-out branch
fast-forwards only in its owning worktree when Git can prove the index,
working tree, operation state, untracked paths, sparse checkout, submodules,
and other worktrees safe. Otherwise Hub records `checkout_sync_pending`,
leaves every byte of user state unchanged, and retries on a later run or
other mutating entry point. Pending dirty checkouts persist the exact blocking
host paths from Git status in the outbox, task results, and plain/JSON/live
events. Commit or stash those paths, then retry the same run; do not run
`tasks recover`. archLoop never stashes, replays, creates hidden
WIP commits, switches branches, force-resets, or runs user hooks during
background projection. Pending checkout sync does not change `shipped` and
does not block later tasks. A remote repository is not required. `shipped`
means the verified candidate is on the publish target and the Beads task
closed with matching transaction metadata. If a run is interrupted, the next `archloop run`
reconstructs missing checkpoints from those durable refs, artifacts, and
receipts, then finishes close and cleanup without landing or closing twice.
Pending reconciliation is not a task failure and does not require
`archloop tasks recover`.

On upgrade, already closed historical tasks stay completed and do not need new
landing receipts. An in-flight task whose source branch is contained in the
configured target is adopted into a new verified transaction automatically.
A historical `merge_succeeded` event is never landing proof. Missing or
diverged branch evidence becomes a `legacy_landing_integrity` condition for
inspection; Hub does not silently close or reimplement that work.

Two runs for the same project or the same task share a landing lease identified
by owner nonce, process start identity, and boot identity. A live owner is not
displaced just because a TTL elapsed. Compare-and-swap checks the expected
target and fence OIDs atomically, so a paused or stale owner cannot land after
the fence or target changes. If the publish target drifts before landing, Hub
invalidates that candidate and verification artifact, rebuilds on the new
target, and fully reverifies the exact OID before retrying CAS. Lease, lock,
and CAS contention stay pending for automatic retry. Plain and JSON output
include the expected and observed target/fence OIDs and distinguish rebuild,
pending contention, stale-owner rejection, and successful landing. Checkout
pending and checkout success are distinct events (`checkout_sync_pending`,
`checkout_sync_succeeded`) in plain and JSON output. Dirty pending events
include the exact blocking host paths. Branch divergence persists observed
host-branch and publish-target OIDs plus the ahead/behind/diverged/missing
relation on the outbox and in plain/JSON/live events. Hub reports
`completed_with_pending_checkout_sync` instead of a generic run failure,
explains that it will not stash, reset, force-update, or overwrite the host
branch, and asks you to reconcile histories manually before retrying the same
flow. With an explicit
`--publish-policy best_effort` and `--remote-target`, local shipped proof also
enqueues a durable code-publication outbox. Network, credential,
protected-branch, and unknown push outcomes stay `target_publish_pending`
without undoing shipped; code publication is separate from GitHub task sync
(`target_publish_pending`, `target_publish_succeeded`). Discovering `origin`
alone never enables publication.

If a legacy task branch committed known Beads runtime/export files
(`.beads/issues.jsonl`, `.beads/interactions.jsonl`, `.beads/events.jsonl`,
and other allowlisted Dolt/backup/lock paths), Hub strips only those paths
from the landing candidate and records them on the transaction and
OID-bearing events. The task branch, user checkout, and `.beads/redirect`
are not rewritten. Beads configuration, documentation, hooks, and unknown
`.beads/**` paths remain ordinary source changes.

One task's failure does not roll back a shipped sibling or skip an independent
waiting sibling. Semantic Git conflicts get at most two merge-role Agent
repairs for the same merge input; verification failures get at most two
candidate-repair attempts, each producing a new candidate generation and a
full re-verification. Repair budgets survive target drift and process restart.
Exhaustion blocks only that task as `merge_conflict_unresolved` or
`verification_failed`. Mixed shipped and blocked outcomes report
`partial_failed`, with each selected task's outcome, reason, transaction id,
and candidate OIDs in plain and JSON output. All-pending batches (for example
`host_contribution_conflict` or lease contention) report batch status
`pending` and run outcome `completed_with_pending_merge` — not shipped and not
a semantic task failure. Transient lock and I/O errors stay pending for
automatic retry.

Task-board implementation and review agents receive an immutable snapshot of
the selected task, its parent PRD, required dependencies, comments, and remote
refs. They do not need live `bd show` access. Structured `<task-notes>` output
is schema-validated and applied by Hub after the attempt; invalid notes are
rejected without changing the live task store.

A Hub implementer iteration that aborts during provider startup with no agent
output does not fail the whole run while iterations remain. The next iteration
continues with a progress summary. The run still fails after the iteration
limit if there is no completion signal and no branch work.
