---
title: Troubleshooting
description: Diagnose archLoop by symptom and choose the least destructive recovery action.
---

Start with:

```bash
npx archloop project status
npx archloop check
npx archloop tasks doctor
```

## No project is selected

**Cause:** the Hub has no selected project, or the previous selection no longer
exists.

```bash
npx archloop project list
npx archloop project select <name>
```

## Registered repository path is missing

**Cause:** the repository moved after registration.

```bash
npx archloop project relink <project> --path <repo-path>
```

## Git repository has no initial commit

**Cause:** worktrees and branch-based execution need a real commit as a base.

Create the repository's intended initial commit, then rerun `archloop check`.

## Task store redirect is invalid

**Cause:** `.beads/redirect` points at a missing or inaccessible Hub-owned
Beads directory.

```bash
npx archloop project status
npx archloop tasks init
```

Fix the redirect path, or rerun `tasks init` for the registered project to
recreate the Hub-owned store and redirect. Do not initialize a second database
in the Git repository.

## Redirect points at a task snapshot directory

**Cause:** A crashed or raced parallel Agent attempt left `.beads/redirect`
pointing at a `task-snapshots/...` attempt directory instead of the managed
store. Snapshot directories are not Beads databases.

```bash
npx archloop project status
```

Restore the redirect to the verified Hub-owned store under the project
directory. Do **not** run `archloop tasks init` for this recovery. After the
board is readable again, recover any claim-only interrupted tasks with
`archloop tasks recover <task-id>` if needed.

## Legacy Beads store still lives in the repository

**Cause:** The project still has a repository-local Beads database. Hub
migrates a writer-free legacy store automatically on the first mutating
`archloop run` or task command.

No extra migration command is required. If a previous attempt crashed, retry
the same mutating command; Hub resumes from the durable journal and backup.
If an external `bd` writer or migration owner is active, Hub defers the switch
and keeps using the verified legacy store until the next automatic retry.
Do not run `archloop tasks recover` for this.

Fresh projects that initialized the task store during `project add` already
own a Hub-managed store plus redirect. That layout is steady state, not an
interrupted migration, so mutating commands must not ask for a migration
source snapshot.

## Interrupted Hub landing transaction

**Cause:** A previous run stopped between candidate creation, verification,
atomic landing, task close, or cleanup.

```bash
npx archloop run --flow with-review
npx archloop tasks doctor
npx archloop project status
```

The next mutating `archloop run` resumes from durable Git refs, artifacts, and
receipts. It reuses the exact candidate and a matching verification artifact,
recognizes an atomic landing receipt, retries Beads close idempotently for
task-backed landings, and retries cleanup without undoing `shipped`. Synthetic
host-contribution landings (`hub-host-contribution`) complete with internal
journal evidence only — they are not Beads tasks and must never be passed to
`tasks recover` or Beads close. `tasks doctor` is read-only. Pending
reconciliation is not a task failure; do not run `archloop tasks recover` for
this.

## Checkout sync pending

**Cause:** Hub landed the verified candidate on the publish target, but the
configured host branch could not be fast-forwarded without touching WIP,
operation state, sparse checkout, submodules, divergence, or another unsafe
worktree condition.

```bash
npx archloop project status
npx archloop tasks doctor
npx archloop run --flow with-review
```

User state is left byte-for-byte unchanged. `shipped` is unchanged. Clean or
switch the checkout, then rerun the same flow; Hub retries the same outbox
item automatically. Do not run `archloop tasks recover` for this.

## Legacy Hub landing history

**Cause:** The project has pre-transaction merge history from before durable
landing transactions.

```bash
npx archloop run --flow with-review
npx archloop tasks doctor
npx archloop project status
```

Already closed tasks stay completed and do not get manufactured landing
receipts. If Git ancestry proves the task branch is contained in the configured
target, the next mutating `archloop run` adopts that work into a new verified
transaction. A historical `merge_succeeded` event is never enough to mark a
task landed, closed, or shipped. Missing or diverged branches become
`legacy_landing_integrity` for inspection; Hub does not silently close or
reimplement preserved work. `tasks doctor` and `project status` stay
read-only. Do not run `archloop tasks recover` for this.

## Task-store split brain after redirect

**Cause:** After `.beads/redirect` was installed, both the leftover
repository-local database and the Hub-owned store were modified independently.

```bash
npx archloop project status
npx archloop tasks doctor
```

Automatic task-store writes are stopped. Inspect both databases and keep the
intended history. Hub does not merge or delete either store. This is not a
task failure and does not require `tasks recover`.

## Agent role or credential is missing

```bash
npx archloop agent-config show
npx archloop env show
npx archloop auth show
```

Run `archloop initialize` to repair shared setup, or configure only the missing
role or credential with the corresponding command group.

## Docker or Podman is unavailable

Confirm the selected provider is installed and running. If direct host execution
is intentional and safe for the workflow, choose a documented no-sandbox path;
do not silently remove isolation from an existing workflow.

## Run stopped with dirty-file overlap

archLoop lists the source files that overlap the merge result. Commit, stash, or
discard only those files, then rerun the same flow. The merge-ready task and its
branch are preserved.

## Task status disagrees with run history

```bash
npx archloop tasks doctor
npx archloop tasks repair-state <task-id>
```

Use repair only when doctor marks the state as repairable. Preview the mutation
before confirming.

## Failed task has branch work

```bash
npx archloop tasks recover <task-id>
```

Recovery preserves retryable work. Do not delete the branch or worktree first.

## Run ended while tasks still look active

Re-run the same `archloop run --flow ...` command. Startup detects tasks left in
implementation, review, or merge without a live lease and resumes from the next
safe event-backed phase. `tasks list` marks these rows `⚠ interrupted`; JSON
sets `interrupted: true`.

Use `archloop tasks recover --stale` to preview all interrupted routes without
starting a flow, then add `--yes` or confirm interactively to apply them. A run
summary points to this command for real task failures, but points back to
`archloop run` for interruption without failed tasks.

## Implementer exited non-zero after finishing

Hub derives success from observed branch work plus the completion signal. A
recognized trailing provider disconnect does not erase completed work. A
zero-new-commit rerun is also accepted when prior run evidence proves the task
was already merged and closed; a completion signal alone is not sufficient.

## Worktree is already in use

An active lease owns the worktree. Wait for the owning process or use the task
recovery guidance. Do not manually remove lock files.

## GitHub synchronization conflict

```bash
npx archloop tasks resolve <task-id> --keep local
# or
npx archloop tasks resolve <task-id> --keep remote
```

Preview the next `tasks sync` or `tasks push` after resolving.

## Provider connection stalled or timed out

Hub execution retries recognized transient provider failures with backoff unless
the agent already emitted its completion signal. Inspect `project status` and
the run directory reported by the CLI before retrying or recovering the task.

## Run died on a later iteration after an exploration-only turn

A provider startup abort with no agent output (for example a SessionStart hook
failure and `stop_reason: abort`) no longer fails the whole multi-iteration
run while iterations remain. The next iteration continues and receives a
progress summary plus a "make implementation progress" nudge when the previous
turn produced no commits.

The run still records `agent_failed` when every iteration is exhausted with
neither commits nor a completion signal, or when the last remaining iteration
aborts during startup. An already-merged zero-commit rerun with a completion
signal is unchanged — see "Implementer exited non-zero after finishing".

## Preserved worktree after close

The worktree contains uncommitted changes and was intentionally kept to avoid
data loss. Inspect it, commit or move the useful work, then use the normal task
recovery or cleanup command. Avoid force deletion.
