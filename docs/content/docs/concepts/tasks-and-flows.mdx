archLoop uses a local Beads task store as the source of task-board state. For
new Hub projects that store lives under the stable Hub project directory, with
a Git-ignored `.beads/redirect` for direct `bd` discovery. Existing
repository-local stores migrate automatically unless Hub defers an unsafe
switch; split brain after redirect stops automatic writes. GitHub Issues
synchronization is optional and explicit.

## Task lifecycle

User-facing statuses include inbox, needs information, ready for an agent,
in progress, review and merge stages, ready for a human, blocked, failed, done,
and wontfix. The CLI projects these statuses from archLoop-managed labels,
metadata, and run events.

## Task-board flows

- `no-review` — plan a batch, implement tasks, verify, and merge.
- `with-review` — add a reviewer stage before verification and merge.

Tasks within a batch can implement and review concurrently. Eligible branches
land independently onto a Hub-managed local publish target under durable FIFO
and dependency tickets. Speculative candidates form an ordered chain on each
predecessor OID, verify exact OIDs concurrently where dependencies permit, and
land only at the queue head with fenced CAS. Suffix invalidation after
predecessor repair, failure, committed host contribution, or target drift
rebuilds independent successors while dependents stay blocked. Committed
host-target tips (behind, descendant, or diverged) enter the canonical chain
before task candidates continue; uncommitted host WIP is never imported. After
at most three immediate drift rebuilds the queue head retains
`target_quiet_wait` until a stable window resumes automatically without
resetting repair budgets or requiring `tasks recover`. A semantic conflict
or verification failure is repaired in bounded Agent attempts, then fully
reverified; exhaustion blocks only that task. Independent siblings continue to
verified landing, dependents wait for an unshipped prerequisite, and mixed
outcomes report `partial_failed`. Landing does not merge into the user's
checkout. After landing, Hub projects the host branch only when a fast-forward
is provably safe; otherwise `checkout_sync_pending` stays visible and retries
automatically without affecting `shipped`. With an explicit `best_effort`
publish policy and remote target, code publication retries as
`target_publish_pending` separately from GitHub task sync and does not undo
local shipped proof. Concurrent runs share a landing lease and fenced compare-and-swap;
target drift rebuilds and reverifies the queue head before another landing
attempt. Lease and CAS contention stay pending. A crashed landing resumes from
durable evidence on the next run without `tasks recover`. Already closed
historical tasks stay completed. In-flight pre-transaction history is adopted
only when Git ancestry proves the source reached the configured target; a
legacy `merge_succeeded` event never proves delivery. Ambiguous missing or
diverged branches surface as `legacy_landing_integrity` instead of automatic
close or reimplementation.

Legacy task branches that committed known Beads runtime/export files such as
`.beads/issues.jsonl` still land their source changes. Candidate construction
strips only that documented allowlist, records the filtered paths on the
transaction and `integration_candidate_created` event, and leaves the task
branch and checkout untouched. Beads configuration, documentation, hooks,
redirect, and unknown `.beads/**` paths stay in the candidate for normal
review.

Implementer iterations continue past a provider startup abort that produced no
agent output, as long as iterations remain. A turn that only explored (no
commits, no completion signal) nudges the next iteration to start writing
instead of repeating the same reads. Exhausting the iteration limit with no
completion signal and no branch work is still `agent_failed`.

If the same flow already has an unfinished merge-ready batch, a later run
recovers it before claiming new tasks.

## Proposal flows

PRD decomposition and Triage generate structured proposals first. They validate
the proposal and guard against unexpected mutations before applying approved
changes to the local task store.
