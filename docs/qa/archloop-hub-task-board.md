# archLoop Hub Task Board Manual QA

本文档用于人工验收 archLoop Hub task board 第一版。验收目标不是证明每个内部函数正确，而是确认用户能在一个真实 host repo 中完成 Hub 项目识别、Beads 本地任务管理、远端同步、flow 执行进度观察、merge/recovery 闭环，并且旧 `archloop init` 流程仍然可用。

## Scope

覆盖范围：

- `archloop project status`
- `archloop tasks list`
- `archloop tasks show <task-selector>`
- `archloop tasks create`
- `archloop tasks from-prd <prd-ref>`
- `archloop tasks triage`
- `archloop tasks pull`
- `archloop tasks push`
- `archloop tasks sync`
- `archloop tasks comment <task-selector>`
- `archloop tasks recover <task-selector>`
- `archloop run . --flow <id> --input <value>`
- `archloop agent-config path/show/init/configure/set-role`
- Beads 本地任务状态、依赖、评论和 ready queue
- GitHub Issues 作为 remote task source 的 pull/push sync
- agent-driven `prd-decomposition` / `triage` proposal sessions
- reviewer / no-review flow 的执行状态
- per-task merge events、verification gate、local Beads close
- legacy `archloop init` 兼容路径

不覆盖范围：

- GUI task board
- 多 remote task source 同时绑定同一 Beads task
- 自定义 flow registry
- Secret vault / keychain backend
- 非 GitHub 的 remote task source

## Test Environment

建议准备两个仓库：

- `ARCHLOOP_REPO`: archLoop 本仓库，用于运行 build/typecheck 和本地 CLI。
- `TARGET_REPO`: 一个独立测试项目，用于执行 Hub task board QA。

最低环境：

- Git repo 已有至少一个 commit。
- `bd` 在 host `PATH` 上可用。
- `gh` 已登录，并能访问测试 GitHub repository。
- 至少一个可运行的 agent runtime 已完成认证。
- Hub agent roles 已配置，至少包含 `planning` 和 `triage`。
- Docker 或 no-sandbox 路径至少选择其一完成验证。

推荐环境变量：

```bash
export ARCHLOOP_REPO=/path/to/archloop
export TARGET_REPO=/path/to/target-repo
export TEST_GITHUB_REPO=owner/repo
```

从 archLoop 仓库构建本地 CLI：

```bash
cd "$ARCHLOOP_REPO"
npm install
npm run build
npm run typecheck
```

在目标项目中使用本地 CLI：

```bash
cd "$TARGET_REPO"
archloop --help
```

## Scenario 07b: Task-Board Batch Selection And Resume Precedence

Purpose: 验证 task-board flow 的 batch strategy 默认值、override、以及 merge-ready batch 的 resume-first 行为。


```bash
archloop run . --flow <NO_REVIEW_FLOW_ID>
```

- Proposal flows reject `--batch-strategy` and `--max-tasks`.
- When no ready tasks are selected but an unfinished same-flow merge-ready batch exists, Hub resumes merge for that batch before planning new work.
- When ready tasks exist alongside unfinished merge-ready batches, Hub starts a new batch and reports old batch ids as not resumed.

Metrics:

- Default strategy in CLI/batch events: `planned` requested.
- Override strategies honored: 100%.
- Deferred ready tasks remain `ready_for_agent`: 100%.
- Resume-first merge when no ready selection: yes when merge-ready batch exists.

Fail signals:

- Default run claims every ready task without batch metadata.

## Human QA Requirements

Fake-agent tests can validate schemas, state transitions, guarded `--yes` behavior, mutation detection, and Beads apply mechanics, but they cannot validate prompt quality or semantic judgment. Before release, a human must run real-agent sessions for:

- `tasks from-prd` interactive refinement quality, including whether slices are vertical, independently verifiable, dependency-aware, and correctly AFK/HITL classified.
- `tasks triage` recommendation quality, including whether needs-info questions are useful, ready briefs are actionable, wontfix rationale is acceptable, and confidence matches risk.
- `run . --flow prd-decomposition --input <prd-ref>` and `run . --flow triage --input <query>` parity with task shortcuts.
- `--yes` operator experience, including clear reporting of applied versus skipped guarded decisions.
- Proposal transcript and artifact readability for later audit.

## Status And State Invariants

During every scenario, verify these invariants:

- `inbox` means task exists but has not been analyzed.
- `needs_info` means task is incomplete and waiting for reporter/user input.
- `ready_for_agent` means task is fully specified and AFK-suitable.
- `ready_for_human` means human-owned valid work.
- `blocked` means task is specified but blocked by dependency, auth, external system, or identified missing info.
- `failed` means execution failed and recovery is possible.
- `done` means branch merged, verification passed, and local Beads task closed.
- `wontfix` means local Beads task closed with wontfix marker.
- `sync_conflict` means local/remote semantic conflict needs human resolution.

Forbidden task statuses:

- `pending`
- `triaging`
- `waiting_for_review`
- `planning`
- `reserved`
- `claimed`
- `deferred`

Batch-only statuses:

- `planning`
- `partial_failed`
